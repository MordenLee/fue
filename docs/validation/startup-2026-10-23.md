# Studio 开发启动优化

日期：2026-10-23。版本保持 2.0.0。本记录描述源码同步前的本地验证。

## 问题与修改

原主进程先等待 `ensureCore()` 成功，再创建窗口；Core 等待、数据库迁移和首次 Python 导入都表现为没有界面。渲染入口还静态导入全部页面。

现在先创建窗口，Core 和界面并行加载。HTML 提供初始加载内容，React 提供计时、错误和重试；Core 就绪前不挂载业务页面。页面按路由加载，开发环境复用 venv 字节码，生产包仍使用可写的用户缓存。Chroma 与分块依赖延迟至实际使用，Chroma 单例初始化用锁保护。

主进程输出 `[startup] window-created/window-visible/core-ready`，渲染进程输出 `application-ready`；主进程时间从模块加载起算，与下面从 npm 命令起算的时间不同。

## 实测

使用真实 `npm run dev`、隔离的合成资料库和测试 profile。测试钩子拦截窗口 show，不弹出窗口；记录原本会显示的时点，并通过 DOM 检查首页可用。没有调用付费模型，没有终止用户已有 Core。

| 场景 | 从 npm 命令到窗口可显示 | 到首页可用 |
| --- | --- | --- |
| 首次独立 Python 缓存 | 2.80 秒 | 11.16 秒 |
| 开发缓存策略修改后，Core 新进程 | 2.68 秒 | 11.22 秒 |
| 复用 Core，注入一次连接失败并点击重试 | 2.72 秒 | 5.05 秒 |

Python 全新缓存下单独导入应用：修改前 8.80 秒，延迟加载后 6.70 秒。这不等于整段应用启动速度；开发缓存策略在本次整段测量中没有体现进一步降幅。

用户报告的约一分钟等待未稳定复现，不能宣称已定位其全部原因；本次消除了窗口等待 Core 的确定阻塞点，并减少启动加载量。

构建和类型检查通过，90 项 Core 回归测试通过。回归新增独立进程检查，确保应用启动不提前导入 Chroma 和文本分块引擎。用户复测确认启动问题修复。日志及 JSON 在 `artifacts/startup-*`、`artifacts/validation/startup-*.json`，不入 Git。
